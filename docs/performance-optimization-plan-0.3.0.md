# 0.3.0 性能核查与优化计划

核查日期：2026-11-11。依据：`modify.md`、当前 `src`、项目安装的 Three.js 0.180 源码及现有验证工具。

本次交付为代码审计和实施计划，没有修改游戏渲染逻辑，也没有重新打包桌面发行版。文档中的适用建议已纳入以下计划。网页服务检查时未运行，已重新启动并通过访问检查。

## 结论与证据边界

采纳“先测量帧时间尖峰、再逐项对照、不要盲目降低画质”的方法，但不能照抄其嫌疑排序。当前环境探针已经缓存，预编译、GPU 水流、低面数遮挡代理、分档反射和 Bloom 降采样都已经存在。

目前确认的是代码结构和若干实现缺口，并未取得当前版本正常游玩状态下 60–120 秒的 CPU/GPU 分项基准。因此下文的“高成本候选”不等于已经实测确认的卡顿根因，不填写虚构的性能提升比例。

`modify.md` 开头的“独显平均超过 60 FPS、四类效果同时工作”不是本次测量结果。锅炉房和镜盾战斗应分别测试；把镜盾加入锅炉房仅作为额外压力场景，不混同常规游戏负载。不把当前机器、软件渲染器或单一显卡作为玩家设备能力依据。

## 本项目额外发现

### 1. 水流密度投影存在明确接线缺口，先修正确性

`src/water-surface.js` 的 densityPoints 顶点 Shader 只读取 CPU position 属性；GPU 分支虽然设置 GPU_DRAIN define，但 Shader 没有相应分支，也没绑定粒子位置纹理。GPU 模拟开启后 CPU 粒子数组为空，投影却按 2400 个顶点绘制，无法代表真实粒子分布。airborne 粒子读取 GPU 位置，并不意味着 densityPoints 也读取了。

影响范围：沟渠覆盖、地表薄膜，以及传回水流积分的二维压力梯度。需独立 GPU 密度纹理取样验证，不能以“水束看起来在喷水”作为通过标准。

计划：GPU 分支直接按粒子索引采样位置和存活时间，CPU 分支保留；验证不同水阀的密度位置、干燥区域为零、停止喷水后消退。测试中可读回小纹理做断言，正式循环不读回。

### 2. 预热没有覆盖所有真正工作的渲染路径

主场景遍历不到 GPU 积分 FullScreenQuad、体积密度 scene、二维密度 scene。当前预热没有主动让四个水阀喷水，也暂时关闭 Reflector 回调，只初始化其目标，因此不能保证真实反射/折射组合已完整预热。

warmScene 展示全部对象并枚举点光源数量进行编译，随后恢复可见性才真正 draw；编译覆盖和实际顶点/纹理上传覆盖不是同一件事。水流启动和停止时还改变 GPU_DRAIN define，可能新增 Shader 变体。

计划：各渲染子系统提供显式 prepare/warmup，按实际场景和能力组合执行少量真实绘制，最后重置状态。不要为了暖场烧掉真实水阀或推进战斗时间。保留 fence 验证，但将超时作为可诊断失败，不静默启用未完成的路径。

### 3. 文档漏掉了体积雾的高片元成本

`src/foundry-atmosphere.js` 的蒸汽和中央光束各做 18 步光线步进，每步两次 3D noise。大屏幕覆盖、透明叠加时，这可能比 2400 粒子积分更贵。

计划：体积雾单独 A/B，必要时低分辨率绘制和深度感知上采样、距离/覆盖率降档；保持蒸汽运动与灯光氛围。不能只优化岩浆而遗漏这层。

### 4. 水束仍有可削减的顶点提交

每条水束 PlaneGeometry(72,12) 为 1728 个三角形；9 条 × 4 个阀门共 62208 个三角形。只要一个阀门喷水，固定四个实例仍被提交，未启用的实例主要靠片元 discard 隐藏。

计划：打包活动水阀实例并同步时间窗，以距离/投影尺寸调整管束段数；与折射成本分别测量，保留近景轮廓。

### 5. 旧性能报告不适合作为流畅性验收

`tools/verify-foundry.cjs` 在同步 for 循环中 draw 后调用 gl.finish 测量 90 次，不是自然 requestAnimationFrame 游玩；它还在原游戏页面创建第二套场景/renderer。旧 `output/foundry-visual-check.json` 的 median/p95 和 GPU 读回时间，只能理解为该验证环境的测试数据，不能推断玩家的正常帧时间。

主游戏目前没有完整帧的 renderer.info 手动累计，也没有 GPU Timer Query 分项统计。单次末尾 render 的数字会漏算水流、阴影和反射等 pass。

## 实施顺序

### P0-A：建立可信基准

1. 独立诊断开关，默认关闭；预分配环形记录缓冲，禁止每帧打印。
2. 在实际游戏循环记录 RAF 间隔、渲染帧间隔、CPU 动画/战斗/镜头/水流/渲染提交耗时、水流步数、Shader 数量和完整帧 draw calls/triangles。
3. EXT_disjoint_timer_query_webgl2 可用时异步采样。限制未完成 query 数量，丢弃 disjoint 结果；不支持时标记“无 GPU 计时”，不拿 CPU 时间代替。
4. 反射嵌套在主场景绘制内，GPU query 不可直接嵌套；先测整体 GPU，再在不同采样帧测独立 pass，不能把包含关系重复相加。阴影也不是项目独立的 renderShadow 函数，不能照抄文档伪代码。
5. 记录浏览器/Electron、实际 renderer、扩展、分辨率/DPR、画质和帧率限制。温度/显存字节等网页拿不到的数据标为缺失或外部采集，不从纹理数量猜测。

交付：可重复基准场景、CSV/JSON 报告、P50/P95/P99/max、>25/33.3/50 ms 次数，以及功能开关事件时间线。

### P0-B：补齐水流正确性和首次使用预热

先保存原版基准，再修 GPU 密度接线；修正后的画面作为性能 A/B 的新基线，不能用“不画出水”冒充优化。

补齐模拟/密度/反射/折射的真实暖场，去掉不必要的 GPU_DRAIN 动态切换。增加水流显式 MAX_STEPS，先对比 2 和 3 步预算、允许积压量以及视觉时间偏差；慢帧允许视觉模拟降低精度，但灭火、伤害等玩法计时不可改变。

### P1-A：减少无收益的重复绘制

镜盾先加实际盾面视锥和投影面积检查，再按运动程度调节更新频率；避免 stale reflection 明显拖影。反射场景过滤不重要的蒸汽、微粒和装饰，测试传输材质是否额外放大反射成本。保留镜面自身隐藏、背面判断和阴影复用。

水束仅提交活动实例。筛选不需要投影的螺钉、细管、灯笼装饰等，必要时共享几何/材质或实例化；不要把所有静态环境合成一个无法合理遮挡和裁剪的大网格。

### P1-B：减少高成本像素工作

优先独立测岩浆、体积雾、折射、Bloom。对真正占比高的模块实施：岩浆共享流场/法线纹理、雾低分辨率、Bloom 独立预算、折射画质档。缓存流场仍在 GPU 计算，目标复用；近景保持现有画风。每项修改都拍同机位对比图，再决定保留。

### P2：CPU 与资源生命周期

遮挡查询加入粗筛和静态代理缓存；复用临时 Map/Set/数组，避免每次全量重建。保留必要的动态代理更新和 75% 遮挡规则。CPU 水流回退复用数组、空间桶和邻居对缓存，并降低预算，不能让兼容路径成为主线程阻塞源。

检查动画重复更新、隐藏敌人和菜单后台工作；以计时证据决定是否改动，避免为了 GPU 化把低成本玩法逻辑搬到 GPU 再同步读回。

建立目标/材质/几何体的所有权和销毁约定。镜面 entries 需在模型卸载时注销；目前常驻缓存不等于已证实泄漏，要用反复进入退出场景验证稳定平台。

## 对照测试矩阵与验收

每项预热后录制 120 秒、至少两次相同轨迹；首次启用卡顿另用全新页面单独测试，不能让预热把首用缺口掩盖掉。

| 场景 | 操作与主要观察 |
| --- | --- |
| 练习场 | 基线移动/攻击/喝药/金光/大招，区分动画逻辑和特效首用 |
| 锅炉房干燥 | 固定镜头与转镜头，分别冻结岩浆、关闭雾、冻结阴影、关闭 Bloom |
| 单阀/四阀喷水 | 模拟暂停保留纹理、独立关闭折射、记录步数和首次喷水编译 |
| 镜盾侍 | 静止/转盾/倒地/屏幕外，冻结反射保留纹理，检查反射正确性 |
| 组合压力场景 | 另行装入锅炉房+镜盾，仅用于压力上界，不代表常规关卡 |
| 长时间/反复切场景 | 10 分钟和 20 次切换，观察资源数量平台、内存与卡顿趋势 |
| 桌面运行时 | 与网页用同份源码测；浏览器/Electron 独立记录，不更新 release |

验收以同设备同条件前后差异为准：目标是 P95/P99 与 >33.3 ms 尖峰下降，不预先承诺未知显卡的固定 FPS。资源预热后无持续增长、首次特效不新增未预期 Shader 编译；水流/镜面/阴影正确，玩法时序不变。

跨设备至少覆盖独显、核显，以及缺少计时/浮点能力的回退组合。可模拟缺扩展验证兼容分支，但不能将模拟结果冒充真实设备性能。所有优化沿用网页与桌面共享实现；需要新安装包时另行发布。

首批执行顺序：可信计时 → 水流接线与首用预热 → 子步预算 → 镜面及水束绘制调度 → 岩浆/雾/折射热点 → CPU 和资源回收。每批保留独立回退点和前后数据。

已接通 GPU 粒子密度投影，湿态预热执行真实积分、密度场、折射和后处理。水流每帧最多计算 3 个 GPU 子步或 2 个 CPU 子步，超过预算时丢弃旧的视觉模拟时间。接下来需完成固定镜头的干燥、单阀、镜盾及分项对照，检查预热的额外编译开销，以及多设备与长时间验收。

设置 `NAIWA_PROFILE_MATRIX=1` 可在同一 Electron 会话依次执行干燥锅炉房、冻结阴影、隐藏雾、隐藏岩浆、关闭 Bloom、单阀、四阀及镜盾的诊断场景。冻结阴影保留已有阴影贴图，关闭 Bloom 保留 HDR 画面输出。隐藏雾或岩浆测到的是整个对应绘制的成本。

首轮每场 7 秒。干燥锅炉房两次基线均为每帧 797 次绘制调用，冻结阴影更新后为 249 次，CPU 帧耗时 P95 从 4.30–4.60 ms 降至 3.10 ms。雾、岩浆和 Bloom 的 GPU 结果在这轮短测中与基线波动重叠。单阀、四阀的画面绘制 GPU 中位数分别为 4.41 ms 和 4.52 ms，高于干燥场景的 2.26–2.50 ms，后续需将水折射与其它湿态绘制拆开。镜盾正常绘制为每帧 105 次调用，冻结后为 66 次，CPU P95 从 3.40 ms 到 2.20 ms。原始数据位于 `output/foundry-profile-matrix.json`。

基于这组结果，墙面按四个区段合批，屋顶接缝按区段实例化，保留原网格形状、材质、投影和窗口开口。镜盾根据实际变形后的盾面包围盒检查视锥，出画时跳过反射，回到画面后继续实时更新。

合批后的同一套 7 秒短测数据位于 `output/foundry-profile-matrix-batched.json`。

| 场景 | 绘制调用中位数，改动前 → 后 | CPU P95，改动前 → 后 | 画面绘制 GPU 中位数，改动前 → 后 |
| --- | ---: | ---: | ---: |
| 干燥锅炉房，两次基线 | 797 → 637 | 4.30–4.60 → 3.70–3.90 ms | 2.26–2.50 → 2.30–2.32 ms |
| 单阀 | 1035 → 834 | 5.40 → 4.70 ms | 4.41 → 2.48 ms |
| 四阀 | 1030 → 830 | 5.30 → 4.40 ms | 4.52 → 2.79 ms |

实际绘制调用在三种场景中都减少约两成。GPU 结果仍需要长测复验，尤其是干燥画面绘制 P95 有波动。两轮各阶段都没有超过 33.3 ms 的渲染帧。同机位干燥画面 1708×1019 像素对比中，只有一个像素的任意颜色通道差值超过 8。WebGL 验证检查了镜盾离开视锥后隐藏、进入后恢复，保留了蒙皮跟随测试。

水折射专项使用 `NAIWA_PROFILE_MATRIX=refraction`，每场 10 秒，保留水流模拟、水束与沟渠绘制。单阀的两轮对照均从每帧 834–835 次绘制降至 645 次，四阀从 830 次降至 644 次。四阀的 GPU 画面绘制中位数由 3.05 ms 到 2.60 ms，P95 从 4.73 ms 到 5.17 ms。单阀 GPU 中位数的两个对照方向不同。绘制调用降幅可重复，GPU 长尾仍需长测。原始数据位于 `output/foundry-profile-refraction.json`。

设置新增「水体画质」。默认高档使用原屏幕折射，性能档改用环境反射、低不透明度的水材质与原有水花。两档共用水流密度、排水动画和玩法判定。`NAIWA_PROFILE_MATRIX=soak` 用四阀分别测两次高档与两次性能档，默认每次 120 秒。

CPU 回退密度求解器现在复用空间索引、邻居对和数值缓冲区。用 0–2400 个点、相同种子及不同规模连续求解进行数值对照，粒子坐标和最大密度与改动前完全一致。局部 Node 测试中，2400 点两次求解耗时中位数从约 4.03–4.11 ms 降至约 3.59–3.61 ms。该测试仅覆盖密度求解阶段，仍需模拟缺少浮点扩展的完整浏览器流程。

四阀喷水的 120 秒长测已完成四轮，按高档、性能档、性能档、高档的顺序运行，原始记录为 `output/foundry-profile-soak.json`。每轮约 7200 帧，均无超过 33.3 ms 的渲染帧。

练习场、镜盾侍、四阀锅炉房顺序循环 20 次，共采样 60 个场景。每个场景的最后五轮峰值计数均稳定在 86 张纹理、282 份几何体、747 个着色器程序，无浏览器错误。原始记录为 `output/foundry-scene-cycles.json`，该轮使用镜面资源释放改动前的场景代码。

镜头遮挡现在按相机与 20 个探测终点的包围盒先筛选碰撞代理，再运行现有精确射线。复用查询容器，并在实例数量或矩阵改变时刷新其边界。600 帧的 Node 场景对照中，包含相机转动、动态实例数量和场景隐藏恢复，遮挡及淡出状态逐帧一致，局部 CPU P95 从约 0.316 ms 降至 0.233 ms。镜面所属模型脱离场景时会同时释放反射目标、材质和克隆几何体，常驻隐藏模型继续复用原目标。

首次喷水专项使用全新页面，进入锅炉房后先记录 120 个干燥帧，再在已开始记录的情况下打开四阀。原预热实现下，首次进入时最大帧间隔约 9983 ms，首次喷水约 2117 ms。喷水当帧的渲染提交约 2126 ms，新增 5 个着色器程序。改为在加载界面预热实际战斗机位、敌人、灯光、完好与破损阀门，再进入游戏，复测最大帧间隔分别为 33.3 和 16.8 ms，着色器程序在喷水前后均为 689。数据位于 `output/foundry-first-use-before-encounter-warmup.json` 与 `output/foundry-first-use.json`。此改动把编译放在加载阶段，测试未比较加载阶段总用时。

兼容性脚本模拟同时缺少浮点颜色附件与 GPU 计时扩展。实际战斗取得 123 个样本，每帧最多 2 个 CPU 水流步，GPU 计时样本为零。单独检查回退路径时，633 个粒子中 265 个进入排水渠，无越界记录，重置后粒子归零并隐藏水面。记录为 `output/foundry-fallback.json`。

Electron 请求低功耗适配器后，WebGL 明确报告使用 AMD Radeon 核显。四阀、高档、1280×802 时，CPU 帧耗时 P95 为 5.60 ms，GPU 画面绘制 P95 为 63.50 ms，帧间隔 P95 为 216.7 ms。水流 GPU 更新 P95 仅 0.168 ms。当前核显的主要压力在画面绘制，高档仍会明显掉帧，进一步对照各项质量开关。

同一核显单项对照中，关闭水折射后的 GPU 绘制 P95 为 52.10 ms，仍不足以恢复流畅；单独冻结阴影、隐藏雾或岩浆、关闭 Bloom 的 GPU P95 均约 60 ms。使用游戏现有设置组合后，四阀场景 GPU 绘制 P95 为 10.31 ms，帧间隔 P95 为 16.7 ms。该组合为分辨率 960×540（当前窗口实际 861×540）、光照低、阴影低、反射低、后处理关闭、水体性能。记录为 `output/foundry-integrated.json`。当前测量支持通过现有档位组合降低画面成本，单项试验还不足以支持为岩浆或体积雾牺牲画质。
